6  MongoDB Atlas to R: Connecting, Pipelines, and Text Analysis

NoteWhy this matters

You can’t analyse a dataset until you can pull it out of Atlas and into a tidy data frame — and once you can, the next skill is knowing how to shape and summarize it before it crosses the network, so a few hundred thousand documents don’t turn a five-minute script into a fight with your machine’s memory. This sheet covers both: connecting and querying, writing and reasoning about aggregation pipelines, and doing tidyverse/text-mining work in a size-conscious way.

Tip

The starter template’s src/main.R (Chapter 4) has an empty connect_to_db() function waiting for you — that’s where the connection code below goes.

It’s written against the AI Incident Database schema, so the field names below match what you’ll actually see, but the thinking process, how to read a pipeline, how to build a new one from scratch, how to avoid downloading more than you need, carries over to any MongoDB collection you work with.

6.1 What you’ll need

  • R (4.x) and RStudio (or Positron / VS Code with the R extension)
  • The connection string for your Atlas cluster (competition organisers will give you this; it looks like mongodb+srv://<username>:<password>@ai-incident-database.ugkyb5n.mongodb.net/)
  • The database name is aiidprod

Install the packages you’ll need once, up front:

install.packages(c(
  "mongolite",   # connect to MongoDB and pull data into R
  "tidyverse",   # dplyr, purrr, ggplot2, tidyr, etc.
  "tidytext",    # tokenisation, sentiment lexicons, tf-idf
  "jsonlite",    # handling nested JSON/BSON fields, building pipelines as lists
  "textclean",   # cleaning up messy text (contractions, HTML, etc.)
  "wordcloud2",  # optional, for word cloud visuals
  "widyr"        # optional, for word-pair / correlation analysis
))

mongolite is the simplest way to talk to MongoDB from R, and it hands data back as a data frame, which is exactly the shape tidyverse tools expect. Both $find() (simple queries) and $aggregate() (multi-stage pipelines) live on the connection object it gives you.

6.2 Know your collections before you query

The schema you’ve been given defines several collections. The two you’ll care about most are:

  • reports — the actual documents/articles. This is where the free text lives. Key fields:

    • _id (objectId), report_number (number) — report_number is the human-friendly key used to link a report to the incident(s) it belongs to
    • title, text, plain_text — text may retain markdown/HTML formatting from the original source; plain_text is the cleaned version and is almost always what you want for tokenising/sentiment work
    • description — a short editor-written summary, separate from the report body
    • authors, submitters — arrays of strings
    • tags — array of free-text tags
    • language, source_domain, url
    • date_published, date_submitted, date_downloaded, date_modified
    • embedding — a precomputed vector embedding of the text (nested object with a vector field); large, and you generally won’t need it unless you’re doing similarity/clustering work directly on the provided vectors
    • is_incident_report (boolean)

  • incidents — the higher-level “event” that one or more reports are describing. Key fields:

    • _id (objectId), incident_id (number)
    • title, description, date
    • reports — an array of report_number values (not full documents) pointing back into the reports collection — this is how you join the two collections
    • Alleged deployer of AI system, Alleged developer of AI system, Alleged harmed or nearly harmed parties — arrays of entity-name strings
    • implicated_systems — array of strings
    • editors, editor_notes

  • classifications — tagging/label data (an attributes field) that links back to incidents/reports by their IDs — useful if you want to bring in categorical labels alongside the report text.

  • entities — a lookup table of named entities (entity_id, name) referenced by the “alleged deployer/developer/harmed parties” fields above.

For most text-analysis tasks, you’ll mainly work with reports.plain_text, optionally joined to incidents for grouping/labels — which is exactly the join used as the worked example throughout this sheet.

6.3 Connecting to the cluster

Never hard-code your username and password directly into a script you might commit to GitHub or share with teammates. Use an .Renviron file instead.

Create/edit your .Renviron file (run this once):

usethis::edit_r_environ()

Add a line like this, save, and restart R:

MONGO_URI="mongodb+srv://myusername:mypassword@ai-incident-database.ugkyb5n.mongodb.net/"

Now connect from your script — one connection object per collection:

library(mongolite)

db_name <- "aiidprod"

reports_conn <- mongo(collection = "reports", db = db_name,
                       url = Sys.getenv("MONGO_URI"))

incidents_conn <- mongo(collection = "incidents", db = db_name,
                         url = Sys.getenv("MONGO_URI"))

# quick sanity check
reports_conn$count()
incidents_conn$count()

If $count() returns a number rather than an error, you’re connected. This number is also your first data-volume signal.

6.4 The core mental model: pipelines are JSON, R is the courier

$aggregate() sends a pipeline to MongoDB’s aggregation engine and gets back a data frame. The key thing to internalize: the pipeline itself is not R code — it’s JSON. You’re writing MongoDB’s own query language as a string, and R is just the courier. That means:

  • Field names are quoted strings ("report_number"), not R symbols.
  • $ in front of a name ("$incident") means “the value of this field,” not an R accessor.
  • The whole thing is an array ([ ... ]) of stage objects ({ ... }), executed top to bottom.

Think of a pipeline as an assembly line: each stage receives the documents from the stage before it, transforms them, and passes the result to the next stage. Nothing is “queried” all at once — it’s a sequence of transformations.

pipeline <- '[ ... ]'   # a JSON array, written as an R string

reports_with_incident <- reports_conn$aggregate(pipeline) |>
  tibble::as_tibble()

6.5 Don’t download the whole collection

It’s easy to fall into this pattern:

library(tidyverse)

report_cols <- '{
    "_id": 1, "report_number": 1, "title": 1, "plain_text": 1,
    "description": 1, "tags": 1, "authors": 1, "language": 1,
    "source_domain": 1, "date_published": 1
  }'

reports <- reports_conn$find(fields = report_cols) |> as_tibble()

glimpse(reports)

Notice what this does: $find() with no query argument means “give me every document in the collection.” fields trims the columns, but it does nothing to trim the rows — you’re still pulling every document over the network and materializing it in R’s memory before you’ve filtered, grouped, or summarized anything. On a small collection this is harmless. On a collection with hundreds of thousands of documents (especially ones with a plain_text field, which tends to be large — or an embedding field, which is a full numeric vector per document), it’s the single most common source of slow, memory-hungry R/Mongo scripts.

The general rule: MongoDB is a database with its own query and aggregation engine — use it as one. Only bring rows into R once they’re already filtered, grouped, or reduced to roughly the size you actually need for the next step.

6.5.1 Filter rows on the server with query

$find() takes a query argument (the same JSON $match-style filter used in aggregation):

# Downloads everything, then filters in R — avoid this
reports <- reports_conn$find(fields = report_cols) |> as_tibble()
recent  <- reports |> filter(date_published >= as.Date("2023-01-01"))

# Filters on the server, only recent documents cross the network
query <- '{ "date_published": { "$gte": { "$date": "2023-01-01T00:00:00Z" } } }'
recent <- reports_conn$find(query = query, fields = report_cols) |> as_tibble()

# Also useful: language filter, straight from mongolite's query syntax
reports_en <- reports_conn$find(
  query  = '{"language": "en"}',
  fields = '{"_id": 1, "report_number": 1, "title": 1, "plain_text": 1}'
) |> as_tibble()

For the full query syntax mongolite supports, see https://jeroen.github.io/mongolite/query-data.html#query-syntax.

6.5.2 Let $group summarize before it ever reaches R

If your end goal is a summary (counts, averages, distinct values), don’t pull raw rows into dplyr::group_by() |> summarize(). Do the equivalent with $group in an aggregation pipeline, so only the summary — not the underlying documents — travels over the wire:

pipeline <- '[
  { "$match":   { "language": "en" } },
  { "$group":   { "_id": "$source_domain", "n": { "$sum": 1 } } },
  { "$sort":    { "n": -1 } },
  { "$limit":   20 }
]'

top_domains <- reports_conn$aggregate(pipeline) |> as_tibble()

This never materializes the full reports collection anywhere — Mongo does the counting, and R receives 20 rows. The date_published year-grouping example below follows the same idea:

reports_per_year <- reports_conn$aggregate('[
  { "$group": {
      "_id": { "$substr": ["$date_published", 0, 4] },
      "n": { "$sum": 1 }
  }},
  { "$sort": { "_id": 1 } }
]') |> as_tibble()

6.5.3 Count before you fetch

Before running any $find()/$aggregate() without a filter, get a sense of scale first:

reports_conn$count()                             # whole collection
reports_conn$count('{ "language": "en" }')        # a filtered subset

If that number is larger than you’re comfortable holding in memory (as a rough guide: tens of thousands of documents with large text fields), that’s your signal to filter further, project fewer fields, or move to the batching approach in 8.5.

6.5.4 limit, skip, and $sample for peeking or paging

# Peek at a handful of documents without downloading the rest
sample_reports <- reports_conn$find(fields = report_cols, limit = 100) |> as_tibble()

# Manual pagination
page <- reports_conn$find(fields = report_cols, limit = 500, skip = 1000) |> as_tibble()

For a genuinely random sample (not just “the first N”), use $sample in an aggregation pipeline instead of limit, since find(limit = ...) returns documents in storage order, not a random subset:

pipeline <- '[ { "$sample": { "size": 500 } } ]'
random_sample <- reports_conn$aggregate(pipeline) |> as_tibble()

6.5.5 A decision guide

Your goal Reach for
A quick look at the data’s shape find(limit = ...) or $sample
Rows matching a condition find(query = ...) or an aggregation $match
A summary/aggregate statistic An aggregation pipeline with $group — never raw rows into dplyr::summarize()
A join across collections, summarized $lookup → $unwind → $group inside one pipeline
Every document, but too many to hold at once $iterate() with batching
“How big is this even going to be?” $count() first, always, before an unfiltered $find()/$aggregate()

6.6 A worked pipeline, stage by stage: joining reports to incidents

This is the actual join you’ll want for this schema — reports linked to the incident(s) that reference them by report_number.

pipeline <- '[
  {
    "$lookup": {
      "from": "incidents",
      "localField": "report_number",
      "foreignField": "reports",
      "as": "incident"
    }
  },
  {
    "$unwind": {
      "path": "$incident",
      "preserveNullAndEmptyArrays": true
    }
  },
  {
    "$project": {
      "_id": 1,
      "report_number": 1,
      "title": 1,
      "plain_text": 1,
      "description": 1,
      "tags": 1,
      "authors": 1,
      "language": 1,
      "source_domain": 1,
      "date_published": 1,

      "incident_id": "$incident.incident_id",
      "incident_title": "$incident.title",
      "date": "$incident.date"
    }
  }
]'

reports_with_incident <- reports_conn$aggregate(pipeline) |>
  tibble::as_tibble()

6.6.1 Stage 1 — $lookup (a SQL-style JOIN)

For every document in reports, MongoDB looks in the incidents collection for documents where incidents.reports matches this document’s report_number. All matches are attached as an array under a new field called incident.

Mental model: “For each report, go fetch related incidents and staple them on as a list.”

6.6.2 Stage 2 — $unwind (flatten the array)

$lookup always produces an array, even if there’s exactly one match. $unwind explodes that array so each matched element becomes its own document (one report + one incident, instead of one report + an array of incidents). If a report matched 3 incidents, $unwind turns 1 document into 3.

preserveNullAndEmptyArrays: true is important — without it, reports with no matching incident would be silently dropped from the results. With it, they’re kept, with incident set to null. Whether you want this depends on whether you’re doing an inner join (drop unmatched) or a left join (keep unmatched) mentally.

6.6.3 Stage 3 — $project (reshape the output)

  • "field": 1 means “keep this field, unchanged.”
  • "new_name": "$path.to.value" means “create a field called new_name, populated from this path.” Since $unwind turned incident into a single embedded object (not an array), you can reach into it with dot notation ($incident.incident_id).

This last step is why the whole pipeline exists: $lookup + $unwind get the related data attached, and $project flattens it into a clean, tibble-friendly shape — no nested lists left for R to deal with.

6.7 The general thinking process for writing a new pipeline

Before writing any JSON, answer these in plain English:

  1. What’s my starting collection, and what’s the shape of one document in it?
  2. What do I want one row of my final output to represent? (One report? One report-incident pair? One tag with a count?)
  3. What has to happen to get from (1) to (2)? — usually some combination of: bring in related data, filter out documents, reshape/rename fields, flatten arrays, or summarize groups.

Each of those verbs maps to a specific stage. Once you can state the transformation in English, the JSON is just translation:

You want to… Stage Notes
Join in data from another collection $lookup Always produces an array field
Flatten an array field (incl. $lookup results) $unwind Use preserveNullAndEmptyArrays deliberately
Filter documents (like SQL WHERE) $match Put this as early as possible for performance
Choose/rename/compute output fields $project 1 keeps, 0 excludes, "$field" copies/renames
Add new fields without dropping others $addFields / $set Like $project but additive — you don’t have to relist every field
Group and summarize (SQL GROUP BY) $group _id is the grouping key; use $sum, $avg, $push, etc. as accumulators
Sort results $sort 1 ascending, -1 descending
Limit / skip (pagination) $limit, $skip Cheapest late in the pipeline, after filtering
Count documents $count Collapses everything into { "count": N }
Random sample of documents $sample Use instead of limit when you want a true random subset
Run several sub-pipelines and combine $facet Useful for “give me totals AND a filtered list” in one round trip
Reshape a document to become one of its subfields $replaceRoot / $replaceWith Common after $unwind when you only want the nested object
Traverse a hierarchy/graph (e.g. org charts) $graphLookup Recursive $lookup

6.7.1 Worked example: $match + $group from scratch

Say you want: “For each source_domain, how many reports were published, restricted to reports published after 2020?”

Walk through the three questions:

  1. Starting collection: reports, each document is one report.
  2. Desired output row: one row per source_domain, with a count.
  3. Transformation: filter by date, then group by domain and count.
pipeline <- '[
  {
    "$match": {
      "date_published": { "$gte": { "$date": "2020-01-01T00:00:00Z" } }
    }
  },
  {
    "$group": {
      "_id": "$source_domain",
      "n_reports": { "$sum": 1 }
    }
  },
  {
    "$sort": { "n_reports": -1 }
  }
]'

report_counts <- reports_conn$aggregate(pipeline) |> tibble::as_tibble()

Notice the pattern repeats: filter/join stages first, reshape stages last. $match should almost always come as early as possible (it reduces the document count before any expensive work), and $project/$group/$sort come afterward to shape the final result.

6.8 Two ways to join reports to incidents — pipeline vs. R-side

WarningJust a demonstration

The following code piece is only a demonstration and is not recommended for use

The example earlier does the join inside MongoDB with $lookup. You can also pull both collections separately and join them in R with dplyr, using incidents$reports (an array of report_numbers):

incidents <- incidents_conn$find(
  fields = '{
    "_id": 1, "incident_id": 1, "title": 1, "description": 1, "date": 1,
    "reports": 1, "Alleged deployer of AI system": 1,
    "Alleged developer of AI system": 1,
    "Alleged harmed or nearly harmed parties": 1
  }'
) |> as_tibble()

# one row per (incident_id, report_number) pair
incident_report_map <- incidents |>
  select(incident_id, reports) |>
  unnest_longer(reports) |>
  rename(report_number = reports)

# now every report row can carry its incident's metadata
reports_with_incident <- reports |>
  left_join(incident_report_map, by = "report_number") |>
  left_join(
    incidents |> select(incident_id, incident_title = title, date),
    by = "incident_id"
  )

Both approaches produce the same shape. Which one to reach for:

  • $lookup/$unwind in a pipeline — join happens on the server, and only the already-joined, already-projected result crosses the network. Preferred when reports is large, or when you only need a subset of the joined result (combine with an early $match).
  • Pull + unnest_longer() + left_join() in R — simpler to read and debug, but as the data gets larger with tokenization (creating a row for each token in plain text) handling all the data in memory is going to be costly.

6.9 Cleaning the text

plain_text is already stripped of most markup, but scraped news text still tends to carry boilerplate (bylines, “read more” links, share-button text). Do a light cleaning pass and keep the original column in case later analysis needs it.

Warning

The following is only a suggestion and is not guaranteed to produce fully cleaned text ready for analysis.

library(textclean)

reports <- reports_conn$find(fields = report_cols, limit = 100) |> 
  as_tibble() |>
  mutate(plain_text = replace_na(plain_text, "")) |>   # guard against NA before cleaning
  mutate(
    text_clean = plain_text |>
      replace_contraction() |>          # "don't" -> "do not"
      replace_url() |>
      replace_html() |>
      str_squish()                       # trim/collapse whitespace
  )

6.10 Tokenising and analysing with tidytext — size-consciously

tidytext works on the “one-token-per-row” principle, which plugs directly into dplyr/ggplot2. Tokenizing multiplies your row count — one document becomes one row per word — so this is often where memory pressure actually shows up, even when the initial find()/aggregate() was fine. Narrow the input before tokenizing.

library(tidytext)

# Bad: tokenize the entire collection at once
# reports |> unnest_tokens(word, plain_text)

# Better: filter server-side to what the analysis actually needs, and
# project away fields (like description, embedding) you don't need here
query <- '{ "language": "en", "date_published": { "$gte": { "$date": "2024-01-01T00:00:00Z" } } }'
subset_cols <- '{ "_id": 1, "report_number": 1, "plain_text": 1 }'

reports_subset <- reports_conn$find(query = query, fields = subset_cols) |>
  as_tibble() |>
  mutate(plain_text = replace_na(plain_text, ""))

tokens <- reports_subset |>
  select(report_number, plain_text) |>
  unnest_tokens(word, plain_text) |>
  anti_join(stop_words, by = "word")

For exploratory work (trying out a TF-IDF approach, testing a topic model), work on a $sample subset first, and only run the full-size version once the approach is validated, the same instinct as testing a pipeline stage-by-stage.

6.10.1 Word frequencies

top_words <- tokens |>
  count(word, sort = TRUE)

top_words |>
  slice_max(n, n = 20) |>
  ggplot(aes(x = reorder(word, n), y = n)) +
  geom_col() +
  coord_flip() +
  labs(x = NULL, y = "count", title = "Most frequent words across reports")

6.10.2 TF-IDF (which words distinguish one incident/domain from another)

Use incident_id or source_domain as the grouping variable to see what language is distinctive to a given incident or outlet:

tfidf <- reports_with_incident |>
  select(report_number, incident_id, text_clean) |>
  unnest_tokens(word, text_clean) |>
  anti_join(stop_words, by = "word") |>
  count(incident_id, word, sort = TRUE) |>
  bind_tf_idf(word, incident_id, n)

tfidf |>
  group_by(incident_id) |>
  slice_max(tf_idf, n = 10) |>
  ungroup()

6.10.3 N-grams

For phrase-level patterns rather than single words:

bigrams <- reports |>
  unnest_tokens(bigram, text_clean, token = "ngrams", n = 2) |>
  separate(bigram, into = c("word1", "word2"), sep = " ") |>
  filter(!word1 %in% stop_words$word, !word2 %in% stop_words$word) |>
  count(word1, word2, sort = TRUE)

6.10.4 Summarize text metrics server-side instead of tokenizing in R

If the final thing you want is a summary statistic derived from text — not the text content itself — MongoDB’s own operators can sometimes get you there without tokenizing in R at all. For example, a rough word count per document with $size and $split:

pipeline <- '[
  {
    "$addFields": {
      "word_count": { "$size": { "$split": ["$plain_text", " "] } }
    }
  },
  { "$project": { "report_number": 1, "word_count": 1 } }
]'

word_counts <- reports_conn$aggregate(pipeline) |> as_tibble()

This computes a number per document server-side and returns one row per document — never the text itself.

7 Combine only the small, already-summarized per-batch counts

total_word_freq <- bind_rows(word_freq) |> group_by(word) |> summarize(n = sum(n), .groups = “drop”) |> arrange(desc(n)) ```

The corpus itself is never fully resident in memory — only one batch, plus a running (and much smaller) frequency table.

7.1 Sentiment analysis

tidytext bundles several sentiment lexicons (bing, afinn, nrc, loughran). Join tokens to a lexicon the same way you joined stop words. loughran is worth knowing about specifically — it was built for financial/news text and includes categories like “uncertainty” and “litigious”, which can be more informative than generic positive/negative for news-style incident reports.

sentiment_scores <- tokens |>
  inner_join(get_sentiments("bing"), by = "word") |>
  count(report_number, sentiment) |>
  pivot_wider(names_from = sentiment, values_from = n, values_fill = 0) |>
  mutate(net_sentiment = positive - negative)

For a numeric score per word (rather than positive/negative labels), use afinn:

afinn_scores <- tokens |>
  inner_join(get_sentiments("afinn"), by = "word") |>
  group_by(report_number) |>
  summarise(sentiment_score = sum(value), .groups = "drop")

get_sentiments() will prompt a one-time download/license confirmation the first time you use a given lexicon — do this well before you need it, in case you don’t have internet access when it matters (e.g. at a competition venue).

7.2 Word co-occurrence / correlation (optional, widyr)

Useful for exploring which words tend to appear together within the same report — do this on a count()-reduced or sampled set of tokens, not the raw full-corpus token table, since pairwise operations grow fast:

library(widyr)

word_pairs <- tokens |>
  pairwise_count(word, report_number, sort = TRUE)

word_cors <- tokens |>
  group_by(word) |>
  filter(n() >= 20) |>          # drop very rare words first
  pairwise_cor(word, report_number, sort = TRUE)

7.3 Debugging and building pipelines incrementally

  • Build incrementally. Write one stage, run $aggregate(), inspect the output, then add the next stage. Debugging a 5-stage pipeline all at once is much harder than debugging it one stage at a time.

  • Comment out stages by truncating the array. Since the pipeline is just a string, you can test '[ stage1 ]', then '[ stage1, stage2 ]', and so on.

  • Watch for the array-vs-object trap. After $lookup, a field is an array. After $unwind, that same field is a single object. Referencing $incident.title only works after unwinding (or if you know there’s exactly one match and use $arrayElemAt).

  • Use jsonlite::toJSON()/fromJSON() to build pipelines as R lists instead of raw strings, if you find quoting JSON by hand error-prone:

    pipeline_list <- list(
  list(`$match` = list(date_published = list(`$gte` = "2020-01-01"))),
  list(`$group` = list(`_id` = "$source_domain", n_reports = list(`$sum` = 1)))
)
pipeline <- jsonlite::toJSON(pipeline_list, auto_unbox = TRUE)

    This trades JSON-string fiddliness for R’s backtick-quoted-name syntax (`$match`) — pick whichever you find less error-prone. Many R/Mongo users stick with raw JSON strings for anything beyond 2–3 stages, since MongoDB’s own documentation and the shell both use JSON, so the translation from “docs example” to “your pipeline” stays literal.

  • preserveNullAndEmptyArrays is a decision, not a default. Always ask explicitly: do I want to drop documents with no match, or keep them with null?

  • Field order in $project doesn’t matter to Mongo, but keeping it consistent with your intended output column order makes the resulting tibble easier to read.

  • Test aggregations in MongoDB Compass or mongosh first, if you have access — it’s faster to iterate there and then paste the finished JSON into your R string than to round-trip through R for every tweak.

7.4 Putting it together: a minimal end-to-end script

library(mongolite)
library(tidyverse)
library(tidytext)
library(textclean)

db_name <- "aiidprod"
reports_conn <- mongo(collection = "reports", db = db_name,
                       url = Sys.getenv("MONGO_URI"))

reports <- reports_conn$find(
  fields = '{"_id": 1, "report_number": 1, "title": 1, "plain_text": 1, "tags": 1}'
) |>
  as_tibble() |>
  mutate(
    plain_text = replace_na(plain_text, ""),
    text_clean = str_squish(replace_contraction(replace_url(plain_text, "")))
  )

word_counts <- reports |>
  unnest_tokens(word, text_clean) |>
  anti_join(stop_words, by = "word") |>
  count(word, sort = TRUE)

word_counts |> slice_max(n, n = 15)

7.5 Common pitfalls

  • Connection refused / timeout — your IP isn’t allow-listed in Atlas Network Access, or you’re on a network (uni wifi, VPN) that blocks the MongoDB port. Test the connection before you need it.
  • Pulling embedding by accident — it’s a full numeric vector per document; leave it out of your fields projection unless you specifically need it, or your find() calls will be slow and memory-heavy.
  • Using text instead of plain_text — text can retain markdown/HTML from the original source, which will pollute your tokens (<, ##, href=, etc.). Prefer plain_text for tokenising.
  • unnest_wider() on the wrong field — authors, tags, and the “alleged parties” fields are arrays of strings, so they need unnest_longer(). unnest_wider() is for fields that are nested objects (there aren’t many of those in reports/incidents).
  • Joining incidents to reports on the wrong key — incidents.reports holds report_number values, not _id (objectId) values. Join on report_number, not _id.
  • Encoding issues (garbled characters) — check Encoding() on your text column and re-encode with iconv() if you see mojibake.
  • Credentials in scripts — always use Sys.getenv() against an .Renviron file, never paste the connection string directly into a script you’ll share or commit.
  • Downloading before filtering/summarizing — the most common source of slow, memory-heavy scripts against this collection specifically; before writing an unfiltered find()/aggregate().

7.7 Summary checklists

Writing any new pipeline

  1. State in one sentence what one output row should represent.
  2. List the stages needed to get there, in order (join → filter → flatten → reshape → group → sort → limit).
  3. Write and test one stage at a time.
  4. Put $match as early as possible; put $sort/$limit as late as possible.
  5. After any $lookup, decide immediately whether you need $unwind, and whether unmatched documents should be kept.
  6. Finish with $project (or $set) so the shape handed to tibble::as_tibble() is already flat and clean.
  7. Before any unfiltered find()/aggregate(), run $count() first.

Size-conscious tidyverse/text-mining work

  1. Ask what the smallest result is that answers your question — a count? a top-20 list? — and try to get MongoDB to produce that directly.
  2. Exclude large fields (plain_text, description, embedding) from fields/$project unless this specific step needs them.
  3. Filter (query/$match) and, for exploration, sample ($sample) before tokenizing.
  4. Prefer $group/$addFields for summaries over pulling raw rows into dplyr::summarize() or unnest_tokens().
  5. If you must touch the full corpus, batch with $iterate() and combine only small, already-summarized pieces — never accumulate raw batches into one growing tibble.
